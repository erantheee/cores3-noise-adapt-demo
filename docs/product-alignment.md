# Demo 产品口径（唯一基准）

最后更新：2026-10-20（目标于 2026-10-19 确认）。本文记录本轮确认的目标与下一阶段范围，覆盖 README 和历史决策中与之冲突的旧口径；不代表新增功能已实现。

## 产品目标

做一个以耳机仓为 AI 算力中心的 OWS 系统，结合环境、佩戴者状态和个人习惯，协调音乐与现实声音，让用户少操作、听音乐更舒服、交流更自然。

最终产品设想由耳机与耳机仓共同感知。耳机仓相对手机处理的实际增量，仍需验证，不能由 Demo 的分工直接证明。

三个体验目标：
- 听音乐时：根据环境掩蔽有针对性地调音，改善被掩蔽的细节。
- 交流时：判断用户是否参与对话，帮助听清对方，同时协调歌曲 EQ。
- 无需干预时：旁人聊天、电视、自己哼唱等尽量不触发；交流结束后自然恢复。

时间、个人历史与用户纠正属于后续输入，不能写成当前已完成能力。

## 本次 Demo 分工

**CoreS3 感知与决策 → Mac 执行音频处理 → AirPods Pro 播放。**

CoreS3 模拟耳机仓，输出环境分析与控制意图；Mac 是播放器与原型音频执行器。当前链路不使用 AirPods 双耳原始麦克风或其内部通透 DSP，不能宣称已在 AirPods 内实现目标人声增强。

本地声纹实验在 Mac 上运行 ECAPA 推理，向设备回传身份判定。这是实验性辅助识别，尚不满足逐帧声纹匹配在端侧的最终目标。

## 音乐与现实人声的联动

现实人声增益与歌曲 EQ 是两个不同控制量，但允许同时执行。对话时不要求歌曲 EQ 归零。

目标是在保留音乐整体听感的同时，对冲突频段适度让位，再控制现实人声增益。具体频段、深度与恢复速度必须经对照听测确定，不能把抬高歌曲人声频段或降低歌曲总音量当成现实人声增强。

协议中的 FLAT、SONG_EQ、EXTERNAL_VOICE_INTENT、SAFETY_HOLD 是模式标签；单一模式标签不意味着所有音频动作物理互斥。SAFETY_HOLD 的命名也不能证明已具备交通风险识别能力。

## 下一阶段：一个完整场景

**用户听音乐 → 主动和旁边的人交流 → 回到听音乐。**

本阶段主线为音乐环境适应与主动对话时的联动。“别人先叫用户”是否纳入本阶段仍待确认，不因本次文档更新自动扩展范围。

验证至少覆盖：
1. 用户独自讲话：不得仅因本人匹配失败就判成另一人接话。
2. 旁人单独讲话、电视/播客、哼唱、呼吸：记录误触发。
3. 用户开口后对方接话：记录触发是否正确、对方首句遗漏与可懂度。
4. 轮流说话和短暂停顿：记录自己声音延迟回放、门控抖动与对话保持情况。
5. 交流结束：记录音乐恢复时间与自然程度。
6. 安静及持续噪声下听音乐：同响度 A/B，判断调音是否有益。

上述是测试范围，不是已通过的结果。误触发率、遗漏率及各项延迟的通过阈值须在正式测试前确定，不按结果倒改。

## 优化优先级

### 1. 修正身份不确定性的表达

“声纹没有匹配到本人”不等于“确认是另一人”。明确区分本人、确认的其他说话人、无法判断；低匹配分本身不能作为换人的充分证据。先解决这个逻辑，再调触发阈值。

### 2. 分开测量三类响应时间

- 开口到正确动作：包括声纹窗口、更新周期、对话确认和动作渐变。
- 原声到耳机中继声：测完整声学链路，不能只报播放端队列。
- 交流结束到音乐恢复：同时评估抖动与主观自然程度。

本地声纹窗口为 3 秒、每秒更新，不能用端侧小模型的微秒级前向时间代表整条响应速度。历史队列与驱动延迟是特定配置的测量/估计，不应称为不可改变的物理下限。

### 3. 验证音乐与现实人声的联合处方

保留歌曲 EQ，在冲突频段适度让位。先用同响度对照评估对方可懂度与音乐完整性。“演示明显”的配置可以保留，但需与听感评估配置明确区分；更响或削波不能作为改善的证据。

### 4. 真实数据验证后再让情境模型参与决策

先选一个实际有用的判断，例如稳定噪声与附近说话，使用 CoreS3 真实场景数据和冻结评估集验证。可靠后只影响一个有界动作；低置信度时回退到保守策略。合成数据准确率不作为真实使用准确率。

### 5. 统一版本与文档

明确 GitHub 主分支、本地未提交实验、设备运行固件及测试记录的对应关系。文档更新不代替代码提交、固件部署或真人验证。

## 展示与验收纪律

- 音乐默认暂停，由用户手动播放；曲目数量不作为本阶段成功标准。
- UI 分开显示设备决策、Mac 执行状态、实际输出路由。
- 当前无耳机播放回执，不得把 Mac 已执行或已选中 AirPods 写成已验证耳机出声。
- 环境音门控打开不能称为目标人声分离。
- 失败结果同样记录；没有合适现场条件时保留当前版本，待条件具备后再开展真人测试。
