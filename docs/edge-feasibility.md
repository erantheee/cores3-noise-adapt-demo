# 端侧可行性论证

这份文档是本仓库的定位依据。它说明**这个项目要回答什么问题**、**用什么量回答**、以及
**哪些结论目前还不成立**。改动本仓库的行为之前请先读这份文档；改动量测口径时请同时更新它。

---

## 一、这个项目要回答什么

目标形态是一个**带感知与计算能力的耳机盒**：盒子有自己的麦克风、处理器和电池，常开感知，
端侧决策，然后把参数交给负责音频的设备。耳机里没有这些。

因此本仓库验证的**不是算法好不好**——那件事已经由
[`ows-earbud-demo`](https://github.com/erantheee/ows-earbud-demo) 在 Mac 上完成并留下了实测数据。
本仓库验证的是另外三笔账：

| # | 待回答 | 为什么 Mac 回答不了 |
|---|---|---|
| 1 | 端侧的**分段延迟**在可接受范围吗？ | Mac 上不存在"端侧"这个约束 |
| 2 | 端侧的**近场拾音信噪比**够不够支撑判断？ | Mac 麦克风位置与形态都不同 |
| 3 | **声纹选人**在端侧可行吗？ | Mac 上算力不构成约束，端侧构成 |

给决策者的表述应当是：**同一套补偿逻辑，两个执行者**。音频链路由播放端负责（这是真实产品的
分工），端侧负责常开感知、判断与决策。唯一变量是"谁在做决策"。

## 二、当前基线（来自 OWS 仓库的实测，不是本仓库的结论）

引用时必须连口径一起引用。

| 指标 | 数值 | 出处与口径 |
|---|---|---|
| 蓝牙链路往返延迟 | **311 ms** | 驱动自报值，与 SNR 无关；chirp 旁证 ≈360 ms |
| 近端中继所需的延迟 | **< 10 ms** | 差 40 倍量级，因此"复制对面的人"做不到透明 |
| Mac 麦克风说话/安静信噪比 | **0.9 dB** | 绕开全部代码直接用 AVCaptureSession 实测 |
| 四个 VAD 判据的表现 | 全部失败 | 分类器置信度 1.00x、语音带能量占比 1.02x、音节率 1.16x、全带 RMS 0.97x |

**0.9 dB 这一条是本仓库动机的来源。** OWS 文档自己的结论是"任何信号处理都救不了 0.9 dB 的
信噪比"，可行补救只有"说大声靠近"。但同一份文档也给出了原因：耳机麦贴在嘴边，信号和环境
噪声一起衰减，**信噪比反而比笔记本麦好一个数量级**。

CoreS3 的麦克风就在设备上。拿在手里跟人说话时离嘴很近——这正是"贴着嘴边的麦克风"，而且它
不需要充当音频链路，所以没有 HFP 降质代价。**待验证的问题因此变成：近场拾音能把 0.9 dB
提高到多少。** 这是本仓库第一笔要量出来的账。

## 三、已经在真机上测到的数字

当前固件（控制节拍 100 ms），CoreS3（ESP32-S3 @240 MHz），设备空载运行，实测：

| 阶段 | p50 | p95 | max | 说明 |
|---|---|---|---|---|
| 采集间隔 | **100.03 ms** | 100.03 | 100.05 | 就是控制节拍本身 |
| 24 频段分析 | **7.02 ms** | 7.03 | 7.03 | 占节拍的约 7% |
| 声纹推理 | 0.000 ms | — | — | **未实现**，如实报 0 |
| 决策 | **0.06 ms** | 0.06 | 0.06 | 60 微秒 |
| 打点自身开销 | 1.52 µs | — | 2.00 µs | 两次读时钟 |

**结论：端侧本机这一段不是瓶颈。** 分析与决策合计 7.1 ms，占 100 ms 节拍的约 7%，
剩下的约 93% 是余量。所以"AI 处理慢不慢"这个问题的答案，在端侧是明确的；
真正占大头的是音频通路本身（蓝牙 311 ms），而那一段与端侧算力无关。

**仍未测的**：连续运行一小时的漂移。需要设备在场时跑 `tools/drift_capture.py` 采集。

### 这一轮从真机数字里修掉的三件事

这三条都**只在真机上暴露**，桌面机上完全看不出来。它们也是"必须先上真机再谈优化"的证据：

1. **分析耗时差了一个数量级。** `goertzel_dbfs` 在每个频段、每个采样点上重算 Hann 窗的
   `cos()`，即每帧 24 × 2048 = 49152 次超越函数调用，而这个窗**与频段无关**。提到循环外后
   降到毫秒级（当前实测 7.02 ms）。桌面机上只快 14%，因为桌面编译器会向量化那段循环，S3 不会——**桌面基准在这里
   会骗人**。
2. **控制节拍超时的真因不是串口日志。** 第一反应是日志阻塞，于是把波特率从 115200 提到
   921600 实测——**周期一点没变，假设被推翻**。真因是读取粒度：节拍判断只能在一次读返回
   之后执行，所以永远"跨过"截止点，平均超出半个读取块。降到 512 样本后过冲回到分辨率附近
   （推理见 `main/app_main.cpp` 的 `kReadBlockSamples` 注释）。
3. **打点开销的度量写错了三次。** 前两版分别报 57 ms 和 7.1 ms——**两次都是把分析本身算进
   去了**，因为结束时刻的读时钟放在了工作之后，而不是紧挨着开始那一次。两次的数字都"看起来
   像个合理的开销值"。现在相邻两次读时钟，1.52 µs。

## 四、三笔账怎么量

### 账 1：分段延迟

不能只报一个总数。要拆成：

```
① 采集间隔          相邻两次分析的间隔（当前节拍下的真实环路周期）
② 帧内计算          NoiseAnalyzer::analyze 实际耗时
③ 声纹推理          embedding 前向耗时
④ 决策              AdaptController::update 耗时
⑤ 传输              BLE notify 发出 → 收到 ACK
⑥ 主机侧生效        播放端回传 applied 时间戳
⑦ 出声              播放端自报设备延迟（当前参照 311 ms）
```

每段报 p50 / p95 / max，并记录连续运行一小时内的漂移。**打点本身的开销必须可忽略**，且要有
断言守住这一点，否则测量会改变被测对象。

口径说明：① 是"相邻两次分析的间隔"，即决策刷新频率，**不等于**"帧里最老那个样本有多旧"。
后者要读 I2S DMA 状态，本轮不做。引用时不要说成"采集延迟"。

### 账 2：近场拾音信噪比

同一句话，两个位置，同一套判据：

| 条件 | 线段⑤ | 对比对象 |
|---|---|---|
| 设备在手里，说话人 10–20 cm | 待测 | Mac 的 0.9 dB |
| 说话人在 1 m 外 | 待测 | — |
| 嘈杂环境本底 | 待测 | — |

双麦克风是否可用**尚未验证**。ES7210 是 4 通道 ADC，BSP 支持多通道输入，但当前固件用的是
`I2S_SLOT_MODE_MONO` 且 `channel = 1`。M5Stack 的文档页是 JS 渲染的，抓不到文本，所以这一项
必须实测，不能假设。

### 账 3：声纹可分性（带止损门）

**先量，再决定要不要投模型工程。**

判据（先定后跑，不许跑完再调）：

| 判据 | 通过条件 |
|---|---|
| 类间间距 / 类内抖动 | ≥ 3 |
| EER | ≤ 5% |

不通过就**停止声纹路线**并如实上报分布数据，退回"波束成形 + 决策层"。这一门存在的理由是本
仓库的姊妹项目已经失败过一次：24 频段频谱包络的类内抖动约 0.15，而人际间距约 0.05，
**抖动是间距的三倍，不存在能分开两组的阈值**。不能再靠"应该可以"往前推。

工具：`tools/voice_separability.py`。所需录音见该工具头部说明。

## 五、声纹链路：三个必须一起做的机制

声纹**不是**一个"训练好存起来"的静态指纹。感冒、距离、环境噪声、说话力度都会让它漂移。
工程上要三件事一起上：

1. **原型 EMA 在线更新**，不钉死模板
2. **每用户自适应阈值**，从该用户历史相似度分布取，不用全局常数
3. **margin 门限**，最像的必须比第二像的明显更像我，否则拒绝判定

另外必须有**自我语音抑制**：开放耳形态下佩戴者自己说话会被自己的麦收进来。

训练与模板存储可以不在端侧（那部分不受延迟约束），但**匹配必须在端侧**，否则延迟与隐私
两条都不成立。

---

## 六、延迟要分两类看，不能混

| 延迟类型 | 量级 | 是否可接受 |
|---|---|---|
| 声纹确认（判断该不该介入） | 0.5–2 s | ✅ 完全可以，且**只能异步做** |
| 声纹匹配（每帧比对，不占音频通路） | < 1 ms | ✅ |
| 提取算法延迟 | 20–50 ms | ⚠️ 勉强 |
| 音频通路（蓝牙） | **311 ms** | ❌ 致命 |

**关键：声纹确认的那一秒是异步的，不影响音频延迟。** 它决定的是"什么时候开始介入"，不是
"声音晚多久到"。真正卡死的是音频通路。

**由此推出一条架构约束**：目标人语音与音乐的混合**必须发生在同一声设备上**。如果语音要经过
"端侧 → 主机 → 蓝牙 → 耳机"，它会多吃 311 ms，结果是听到对方慢半拍说话。因此本项目
**不做音频回传注入**；真实注入要等出声设备本身就是端侧之后再做。

---

## 七、音乐处理的原则

用户对现有产品最大的吐槽是**音乐被压低/被抬高**。因此本项目明确两条：

1. **不做响度闪避。** 音乐总电平不变，只在频域重新分配。
2. **只补不压。** 只对会被掩蔽的低电平成分做提升，响亮成分不动。

这两条与 OWS 的 C/D 版本一致：`CONTENT-AWARE-NOISE-ADAPT.md` 里的让位比例
（讲话/稀疏 0.50、密集 0.25、均衡 0.35）**唯一目的是防止削波**，不是"让音乐变小"。
这个区别在产品叙事上很重要，必须讲清楚。

## 八、判据修复：已完成的账

修复前的实测缺陷（`controller.cpp` 的单阈值逻辑）：

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 白噪声 −45…−25 dBFS | 判为 **人声嘈杂**，媒体音量被压到 73–89% | 非人声，媒体音量保持 100% |
| 1 kHz 纯音 −30 dBFS | `voice_likelihood = 1.00` | 非人声 |
| 500 Hz / 2 kHz 纯音 | 判为人声 | 非人声 |
| 削波信号 | `mic_valid = true` | 麦克风失效 |

修复后的判据用四个描述量相乘：语音带能量占比、语音带峰值集中度、**频谱平坦度**、
**被激发的频段数**，再乘电平门。

**为什么是平坦度而不是频谱倾斜**：早期版本用"频段电平对频段序号的回归斜率"。这个量是
**谐波间距的假象**——120 Hz 语音在低频段每段有几十根谐波，高频段只有一根，测得斜率由
每段落进几根谐波决定，而不是由频谱包络决定。结果是该判据**拒绝语音、放过噪声**，方向完全
相反。平坦度没有这个失效模式。白噪声实测 0.693，语音实测 0.010–0.012，间距 56 倍。

回归覆盖见 `test/noise_analyzer_test.cpp`（39 条断言，修复前会失败）。

**已知边界**：极窄带的高集中度语音仍可能被拒绝（实测一例：voice 0.752 恰好越过峰值门
0.72）。阈值常量在 `controller.cpp` 的 `voice_thresholds` 与 `clip_thresholds` 命名空间里，
**必须用真实录音重新标定**。合成信号只能证明"已知假阳性没了"，不能证明准确率。

## 九、还没有结论的事

已经落地的（真机实测，见第三节）：分段延迟、控制节拍精度、打点自身开销。

**仍然没有结论的，以及各自卡在哪里：**

| 待回答 | 卡在哪 |
|---|---|
| 双麦克风是否可用、方向性增益多少 | 需真机实测。ES7210 是 4 通道 ADC，BSP 支持多通道，但当前固件用 MONO 单通道；M5Stack 文档页是 JS 渲染的，抓不到文本，**不假设** |
| 近场信噪比相对 Mac 0.9 dB 的改善 | 需要人在设备旁录三类音频（近距说话 / 1 m 外 / 嘈杂本底） |
| 判据阈值用真实录音标定 | 同上，当前的 `voice_thresholds` 只由合成信号拟合 |
| 声纹可分性（类内抖动 vs 类间间距） | 需要同一人**分次、换距离换音量**录多条；工具 `tools/voice_separability.py` 已就位，判据已写死 |
| 连续运行一小时的延迟漂移 | 需设备在场跑 `tools/drift_capture.py`；这一项决定"稳定"是可报的结论还是未验证的说法 |
| 端侧跑完整目标人提取（TSE）的实时性 | **存疑，且不在本轮验收内**。最接近的方案 TargetVoice 是 10 MB 编码器 + 12 MB 提取块 + 6 GMACs；内存够（16 MB flash 中 11.94 MB 空闲 + 8 MB PSRAM），但算力接近 ESP32-S3 上限且受 PSRAM 带宽限制 |
| 判据改动对 Mac 侧已排练行为的影响 | 标定值（如 `mediaLeakDB`）**可能需要重跑** |

### 关于"端侧 AI 的真实成本"这一条要怎么说

现在能负责地说的是：**24 频段分析 + 决策在端侧占 7.1 ms，节拍余量约 93%。**
现在**不能**说的是"端侧 AI 很快"，因为：

- 声纹推理**还没实现**，它是这套流程里唯一真正的神经网络负载，报 0 是因为没有，不是因为免费
- 目标人提取（TSE）如果放进端侧，按 6 GMACs 估算是另一个量级的工程，可能吃满算力

所以对外的说法应当是"感知与决策的本机开销已实测，模型负载尚未接入"，而不是"端侧很快"。

## 十、不做的事，以及为什么

| 不做 | 原因 |
|---|---|
| 端侧播放音频 | 音频链路由播放端负责，这是真实产品的分工 |
| 音频回传注入 | 会多吃 311 ms 蓝牙延迟，听到对方慢半拍 |
| LE Audio 直连耳机 | 索尼需 App 发起、Bose 目前只在头戴且限 Android 13+，第三方源插不进去 |
| 响度闪避 | 用户最反感的行为，改用频域重新分配 |
| 云端参与实时通路 | 延迟与隐私两条都不成立；云端只做训练与模板存储 |
