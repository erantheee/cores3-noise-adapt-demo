# Apple「对话感知」的行为与端侧迁移

状态：**触发与时序已实现（分支 `feature/apple-conversation-awareness`），时序参数待真机标定**
最后更新：2026-10-16

---

## 1. Apple 公开了什么（唯一能引用的部分）

Apple 不公开算法，只公开行为。可引用的只有两类：

- **设置面板原文**（macOS 26.7 → 系统设置 → 蓝牙 → AirPods Pro → 对话感知）：
  「开始与他人讲话时降低媒体音量并减少背景噪声。」
- **支持文档口径**（经日文资料转述的官方说明）：开始说话 → 媒体音量下降；
  **说话期间保持低位（接近暂停）**；对话结束 → 恢复。
- **触发条件**：佩戴者**自己**开口，包括独白、哼唱、咳嗽、近距离自己的声音；
  **别人说话不触发**。

三步里，"降低媒体音量"的前后两端（触发、保持/恢复）是本项目要迁移的；
"减少背景噪声"落在 ANC/通透 DSP 上，本项目不做（与状态总表第 17、19 项口径一致），
**迁移范围明确排除**。

## 2. 为什么必须换掉旧实现

旧实现（`main/controller.cpp`，本分支已删除）：

```text
speech_active = voice_likelihood > 0.55 && broadband_dbfs > -58
两轮"语音 → 300–2500 ms 停顿 → 再语音"，或 2.4 s 持续语音
  → conversation = LIKELY，保持 3.5 s，媒体下压到 25%
```

它检的是**"这段音频像不像对话"**，而 Apple 检的是**"是不是我在说话"**。
播客、电视、路人说话都能满足前者 —— 方向就是错的，这也是本轮替换的根因。

## 3. 实现

| 文件 | 作用 |
|---|---|
| `main/conversation_awareness.hpp/.cpp` | 状态机 `idle → confirming → engaged → releasing`，证据与状态机分离 |
| `main/controller.cpp` | 每帧填 `Evidence` 并调用状态机；下压与调音模式解耦；删除旧轮次启发式及其 4 个成员状态 |
| `test/conversation_awareness_test.cpp` | 30 条断言 |

`Evidence::own_voice` 是**唯一触发输入**。参数集中在 `conversation::Params`，并且有
`set_params()` 标定入口，所以标定不需要改状态机、也不需要重新编译调用方。

### 3.1 保真度声明（不能省）

设备上今天**没有**真正的"自身语音"检测器：`voiceprint_gate` 只有接口、主工程没接模型，
IMU 也没进主工程。因此 `main/controller.cpp` 的 `own_voice_proxy()` 用
"近场电平优势 × 语音判据"做**占位**证据。

> **已知缺陷：附近有人大声说话会被误判成佩戴者开口。**
> 接入真正的检测器（骨传导 IMU 或声纹门控）时，只替换这一个函数，
> 状态机与全部时序参数都不动。

## 4. 实测记录（macOS 26.7 / AirPods Pro / 固件 9A348）

工具：`airpods-control/bin/awareness-measure`（50 ms 同步采样输出设备音量 + 麦克风电平；
判定逻辑有 `--replay` 离线验证入口，三种情形——有下压/无下压/无说话——都已用合成数据测过）

| 轮次 | 条件 | 结果 |
|---|---|---|
| run1 | 耳机同时当输入输出；探针播放《渡口》；佩戴者在 5–38 s 说了多段（2.1–3.7 s） | **输出音量全程 0.260，无任何变化**。190 s 处出现 3 次变化，步长恰为 1/16（macOS 音量量化步长），判定为手动按键/耳柄，不计入 |
| run2 | 输入改为内置麦克风（让耳机麦克风空闲）；聆听模式=自适应 | 150 s 内**音量恒为 0.3125**；但麦克风数据里没有 4–6 s 的持续语音段，**本轮无效**（人不在） |

**结论：目前没有测到 macOS 侧的对话感知下压。** 第 3 轮把下面第 2、3 条混淆项去掉了
（输入改用内置麦克风、注册 Now Playing、等佩戴者开口再计时），结论仍待第 3 轮实跑。
尚未排除的可能：

1. macOS 不执行这条功能（只有 iPhone/iPad 执行）；
2. 只有被识别为"媒体会话"的 App 才被下压（探针是 AVAudioEngine CLI，未注册 Now Playing）；
3. 耳机麦克风被宿主占用时该功能被抑制；
4. 与聆听模式/自适应音频相关。

在测到之前，`Params` 里的数字是**待标定值，不是 Apple 的实测值**。

## 7. 已知偏差（迁移带来的行为变化）

- **下压与调音模式解耦**：安静环境下自己说话也会下压；旧实现把下压挂在
  `external_voice_intent` 分支里，所以"环境判据 = quiet → FLAT"时不会下压。
  这是刻意的：Apple 这条功能不挑模式。
- **`conversation` 字段语义变化**：`LIKELY` 从"轮次成形的对话"变成"佩戴者正在说话（正在下压）"。
  协议字段与上位机未改，面板文字不变。

### 9.1 状态机本身是对的

- `speech-01`：第 62 拍下压、第 87 拍开始恢复 —— 触发、保持、恢复三个相位都跑到了；
- `selfvoice`：187 秒里 131 拍处于下压，恢复相位正常结束；
- 全部 8 个素材都没有出现"压下去起不来"。

### 9.2 暴露的两个问题（都不是状态机的问题）

1. **近场代理不是可用的自身语音判据。** `throat_clear-01` 拿到 own_voice = 1.00 并压到 25% ——
   清嗓子被判成"我自己开口"。这与 Apple 自己的用户抱怨方向一致（清嗓/咳嗽/独白都会触发），
   但**在我们这里它是靠电平而不是靠骨传导判出来的**，所以没有可调的选择性。
2. **素材口径的坑又出现了（与状态总表 38h 同源）。** 这批素材是 Mac 麦克风录的，而判据阈值是在
   设备 ES7210 上标定的：`silence` 素材竟有 37/75 拍被判成语音，而真正的 `speech` 素材只有 5/93 拍。
   **这组数字不能用来改设备判据**，只能说明"用 Mac 麦克风素材验证触发选择性"这条路走不通。

### 9.3 所以下一步是换证据，不是调参数

`Params` 里的数字解决不了 9.2：问题在**证据本身**。两条已确认的路线：

- **IMU 骨传导**（Apple 的思路）：自身语音在六轴上有稳定的低频振动特征，与"旁边有人说话"可分离；
- **声纹门控**：`main/voiceprint_gate.hpp` 的接口已经在了，缺的是模型与素材。

两条都需要先在**设备**上录素材（不是在 Mac 上录），否则会重复 9.2 的口径错误。

## 10. 设备端标定素材采集（第一次真机跑通）

### 10.1 为什么要设备口径

第 9 节已经把"用 Mac 麦克风素材验证触发选择性"判了死刑（与状态总表 38h 同源）。
触发标定必须用**设备自己听到的音频**。

### 10.2 16 kHz 是设备端录音的物理上限

README「端侧录音」一节已经算过：48 kHz 单声道 base64 约 **128 kB/s**，串口可用吞吐
约 **92 kB/s**（139%，不可用）。所以设备端素材是 16 kHz，**24 段里 8 kHz 以上的频段
不能用这批素材判定**。判据真正用到的 300–4000 Hz 语音带在 16 kHz 下是完整的。

### 10.3 采集脚本

```bash
# 先让出串口（上位机面板会占着它）
CORES3_PORT=/dev/cu.usbmodem101 sh tools/free_port.sh --kill
./.venv/bin/python tools/collect_conversation_evidence.py \
    --port /dev/cu.usbmodem101 --speaker 甲 --verify
# 采完原样拉回面板
cd tools && nohup ../.venv/bin/python -u -m host --port /dev/cu.usbmodem101 \
    --web-port 8787 --no-browser &
```

类别按**谁在说**分家，这是对话感知与"24 段判据"最本质的区别：

| 类别 | 期望 |
|---|---|
| `self_speech_near`（设备在嘴边 10–20 cm，自己说） | **应该**触发 |
| `self_speech_far`（设备在桌上，自己 1 m 外说） | 触发与否取决于证据质量 |
| `other_speech_near` / `other_speech_1m`（别人说） | **不应该**触发 |
| `podcast`（手机放播客/视频） | 不应该触发 —— 旧轮次启发式会在这里误触发 |
| `throat_clear` / `hum_long` / `breath` / `silence` | 不应该触发 |

每条落盘 WAV + sidecar JSON（时长、块数、丢块、电平、相对本底、可用性）。
**有丢块的录音直接标 `usable=false`**，脚本返回非零，不静默补零。

### 10.4 第一次真机结果：基线就是坏的

2026-10-16 18:40，设备在线、上位机让出串口，采了一条 `silence`（4.01 s、201 块、丢块 0、
电平 −36.7 dBFS），立刻回放：

```
类别          拍数   语音拍   下压拍   最低%   own峰值   判定
silence        75      35      35      25     0.60   DUCKED
```

**设备自己录的"安静"，被判成语音 35/75 拍，并一路压到 25%。** 这就是近场代理的真实水平：
它在设备口径上比在 Mac 素材上更糟，因为代理只是"语音判据 × 电平"，而语音判据本身在这段
本底上就有近一半的帧越线。

注意两条限制：这只有**一条**素材、且是 16 kHz（见 10.2），所以它证明的是"当前证据不可用"，
还不足以给出任何阈值。**要改的是证据，不是门限** —— 与第 9.3 节同一个结论。

## 11. 骨传导自身语音证据（IMU 进主工程）

### 11.1 为什么必须换证据

第 9、10 节把两条路都堵死了：Mac 素材不能判定设备（38h），而**设备自己录的静音**
在近场代理下被判成语音 35/75 拍、一路压到 25%。近场代理的判据是"语音判据 × 电平"，
它没有"这是不是我"的信息。Apple 用的是**内耳麦克风 + 加速度计**的骨传导证据，这一节就是补上它。

### 11.2 搬了什么

| 来源（experiments/ear-context） | 落到主工程 |
|---|---|
| `components/bmi270`（Bosch 官方驱动） | `components/bmi270/` |
| `main/imu.cpp/.hpp`（100 Hz、±4g、±500°/s，先探测 0x68/0x69，映射 DRDY 中断） | `main/imu.cpp/.hpp`（原样，含"没有 DRDY 映射就会静默失败"那条注释） |

新增 `main/bone_voice.hpp/.cpp`：**判据本体**，纯逻辑、无 I2C、无任务调度，因此能在主机上
用合成信号完整测试（18 条断言）。

### 11.3 判据：包络同步，不是振动频谱

100 Hz ODR 的 Nyquist 只有 50 Hz，看不到骨传导语音振动的频带（100–1000 Hz）。但**看得见包络**：
自己说话时，加速度计的振动幅度与音频的语音带电平会**同步起伏**（音节率 2–8 Hz）。
别人说话、外放、走动都不会产生这种同步。所以判据是相关性：

```text
加速度模长 → 去重力（~0.08 Hz 高通）→ 每 100 ms 桶内 RMS（振动包络）
音频 → 第 8–16 段（300–4000 Hz）平均电平
两者在 800 ms 窗内做 Pearson 相关 → 相关性 × 振动幅度 ×（运动否决）
```

想直接看振动频带需要把 ODR 提到 400 Hz 以上，那是下一步。

### 11.4 接线（固件）

```text
app_main：imu_init()  ← **同步、先于音频任务**（见下面的总线理由）
   └─ 队列（深 64）→ 控制任务每拍全部取出 → bone_voice.push_imu(模长, t)
imu_task（5 ms 轮询，100 Hz 采样，优先级 4，低于音频控制任务的 6）
控制任务（100 ms 一拍）→ bone_voice.push_audio(语音带电平, t) → 置信度
   └─ controller.set_own_voice_evidence(evidence)
```

**为什么 IMU 初始化放在 app_main 而不是采样任务里**：BMI270 与音频编解码器**共用 BSP 的
I2C 总线**（`bsp_i2c_init()` 是幂等的，有 `i2c_initialized` 守卫，共享本身没问题）。但音频控制
任务的优先级是 6、IMU 任务是 4，若由 IMU 任务去初始化，音频任务会在初始化中途抢占它，
两次 I2C 驱动安装/设备注册就可能交错。**ear-context 那个实验里两个任务是同级（5），不会互相抢占，
所以照搬它的写法在优先级不同的主工程里并不等价。** 同步初始化同时拿到了"IMU 先于音频"这个
已验证的顺序。IMU 任务栈取 6144（与 ear-context 相同尺寸），不用未验证过的 4 KB。

配对是 1:1 的：控制拍 100 ms、IMU 100 Hz，一拍正好 10 个采样。

### 11.5.1 缺证据时 fail-closed（2026-10-16 决定）

证据来源只有三种状态，遥测里必须分开报：

| `own_voice_source` | 含义 | 会不会下压 |
|---|---|---|
| `bone` | 骨传导 IMU 证据 | 会 |
| `near_field` | 近场代理兜底（调用方**显式**打开开关） | 会 |
| `none` | 没有证据，fail-closed | **不会** |

**为什么默认不拿代理兜底**：代理的判据是"语音判据 × 电平"，它在设备自己录的静音素材上把
**35/75 拍**判成语音并压到 25%（第 10.4 节），而且分不出"自己说"和"旁边人说"。让它在 IMU
挂掉时兜底，等于把"特征暂时不工作"变成"音乐时不时无故被压"——后者难查得多。
代理本身保留：回放工具（`tools/conversation_replay.cpp`）显式打开开关继续用它检验判据形状，
产品路径默认不经过它。

回归断言：`test/controller_test.cpp` 的 "clear speech with no own-voice evidence does not duck
(fail-closed)" 与 "the proxy fallback still exists when a caller opts in"。

### 11.5 测试抓到的两个真 bug（都不是调参）

1. **重力基线时间常数不能靠近相关窗**：第一版取 2 s、窗 0.8 s，基线把"说 3 拍停 1 拍"的起伏
   当成重力吸掉，振动 RMS 变成近似常数、相关系数归零。结论写进了 `Params::gravity_tau_s` 的注释。
2. **RMS 丢符号**：第一版测试用"整拍直流偏置"当振动，于是高通的输出被基线漂移主导、
   相关系数变成 **−1**。真实加速度计读到的是"重力直流 + 振动交流"，所以测试信号改成 20 Hz 正弦；
   这条物理假设也写进了注释——否则下一个人会再踩一次。

另外运动判据的 2 s 时间常数在 2.4 s 内只走到 70%，摸不到 0.35 的门限；改成 500 ms
（走动要在半秒内被认出来，那半秒宁可不触发）。

### 11.6 尚未验证的部分（必须在真机上过一遍）

| 项 | 为什么必须真机 |
|---|---|
| BMI270 是否初始化成功、轴向/重力模长是否正确 | 主机测不了 I2C 与装配方向 |
| 100 Hz 下骨传导信噪比够不够 | 只有戴上/贴住才有真实耦合 |
| 自己说话 vs 别人说话 vs 走动的置信度分布 | 需要第 10 节的设备端素材，且要边录边看 `bone` 置信度 |
| 与音频任务同跑时是否丢采样（`g_imu_drops`） | 调度与 I2C 竞争只有在真机上才出现 |

## 12. 真机验证脚本

`tools/verify_conversation_awareness.py`。它把第 11.6 节那四项做成可重复的检查，并且**按说话人分相**，
因为光看 `media_percent` 分不出下面三件事——它们的修法完全不同：

| 现象 | 真正的问题 | 要改什么 |
|---|---|---|
| 说话相没有下压，且 own_voice 一直很低 | **证据没来** | 骨传导判据 / IMU |
| 说话相 own_voice 很高但没下压 | 状态机或时序 | `conversation::Params` |
| 不该下压时下压了（走动 / 旁人说话） | 门限或运动否决 | 判据门限 |

### 12.1 相位与检查

```text
baseline      静置 10 s      → IMU 就绪、重力基线、静止证据应接近 0
self_speech   自己说话 12 s  → 骨传导证据成立、来源必须是 bone、下压时序
quiet_after   安静 10 s      → 媒体恢复
motion        拿起走动 10 s  → 运动否决生效、不得下压
other_speech  旁人说话 12 s  → 不得下压（可用 --skip-other-speech 跳过）
```

| 检查 | 断言 |
|---|---|
| C1 | 固件是 v3（带自身语音遥测）。**这是闸门**：旧固件直接拒绝跑，避免得出假结论 |
| C2 | 静止相 ≥90% 帧 `imu_ok=true` |
| C3 | 静止相 `imu_gravity` p50 ∈ [9.0, 10.5] m/s²（±4g、单位是 m/s²） |
| C4 / C4b | 每相帧率 ≥80%；整个验证过程 `imu_drops` 增量为 0 |
| C4c | 每相 IMU 采样率 ∈ [90, 110] Hz —— "跑在 100 Hz"必须是量出来的 |
| C5 / C5b | 说话相 own_voice 峰值 ≥0.30 且比静止相高 ≥0.15；来源是 `bone` |
| C6 | 证据（≥0.5）到下压（<60%）≤ **650 ms**（确认 200 ms + 3τ） |
| C7 | 停止说话相 media 回到 100% |
| C8 | 运动相 `imu_motion` 出现过，且全程不下压 |
| C9 | 旁人说话相下压帧为 0 |

### 12.2 怎么跑（含烧写与回滚）

这台设备的串口是 `/dev/cu.usbmodem101`，上位机面板（`tools/host`）会一直占着它。

```bash

cd tools && nohup ../.venv/bin/python -u -m host --port /dev/cu.usbmodem101 --web-port 8787 --no-browser &

# 回滚：outputs/current 就是当前在跑的 3b744cc（SHA256 e742b491…，与 plan-status 记录一致）
CORES3_PORT=/dev/cu.usbmodem101 sh tools/flash.sh
```

烧之前可以先干跑一次：`--dry-run` 只读两秒、确认固件版本，不会执行任何相。

退出码：`0` 全过 · `1` 有断言失败 · `2` 设备/固件不对 · `3` 串口被占。

### 12.3 检查器自测（`--selftest`，不需要设备）

检查器本身必须被验证，否则真机那一次跑出来的报告不能用来决策。`--selftest` 用合成帧跑五个场景，
并断言"预期挂哪几条"与"实际挂哪几条"一致：

| 场景 | 预期失败 |
|---|---|
| `good`（证据到、下压 300 ms、运动否决、旁人不下压） | 无 |
| `no_evidence`（说话相 own_voice 一直是本底） | C5 / C6 / C7 |
| `evidence_no_duck`（证据到但媒体不动） | C6 / C7 |
| `ducks_on_others`（旁人说话也下压） | C9 |
| `imu_dead`（IMU 挂 → fail-closed） | C2 / C3 / C5 / C5b / C6 / C7 |

它当场抓出检查器自己的一个真 bug：**C6 的提示语对"证据没来"和"证据来了没下压"用了同一句话**，
于是后者也会提示"先看 C5"。而把这两种情况搞混，正是这个脚本存在的理由。
这个自测已接进 CI（host-tests job），避免它悄悄退化。
