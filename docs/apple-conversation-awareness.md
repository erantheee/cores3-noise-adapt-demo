# Apple「对话感知」的行为与端侧迁移

状态：**触发与时序已实现（分支 `feature/apple-conversation-awareness`），时序参数待真机标定**
最后更新：2026-10-16

---

## 1. Apple 公开了什么（唯一能引用的部分）

Apple 不公开算法，只公开行为。可引用的只有两类：

- **设置面板原文**（macOS 26.7 → 系统设置 → 蓝牙 → AirPods Pro → 对话感知）：
  「开始与他人讲话时降低媒体音量并减少背景噪声。」
- **支持文档口径**（经日文资料转述的官方说明）：开始说话 → 媒体音量下降；
  **说话期间保持低位（接近暂停）**；对话结束 → 恢复。
- **触发条件**：佩戴者**自己**开口，包括独白、哼唱、咳嗽、近距离自己的声音；
  **别人说话不触发**。

三步里，"降低媒体音量"的前后两端（触发、保持/恢复）是本项目要迁移的；
"减少背景噪声"落在 ANC/通透 DSP 上，本项目不做（与状态总表第 17、19 项口径一致），
**迁移范围明确排除**。

## 2. 为什么必须换掉旧实现

旧实现（`main/controller.cpp`，本分支已删除）：

```text
speech_active = voice_likelihood > 0.55 && broadband_dbfs > -58
两轮"语音 → 300–2500 ms 停顿 → 再语音"，或 2.4 s 持续语音
  → conversation = LIKELY，保持 3.5 s，媒体下压到 25%
```

它检的是**"这段音频像不像对话"**，而 Apple 检的是**"是不是我在说话"**。
播客、电视、路人说话都能满足前者 —— 方向就是错的，这也是本轮替换的根因。

## 3. 实现

| 文件 | 作用 |
|---|---|
| `main/conversation_awareness.hpp/.cpp` | 状态机 `idle → confirming → engaged → releasing`，证据与状态机分离 |
| `main/controller.cpp` | 每帧填 `Evidence` 并调用状态机；下压与调音模式解耦；删除旧轮次启发式及其 4 个成员状态 |
| `test/conversation_awareness_test.cpp` | 30 条断言 |

`Evidence::own_voice` 是**唯一触发输入**。参数集中在 `conversation::Params`，并且有
`set_params()` 标定入口，所以标定不需要改状态机、也不需要重新编译调用方。

### 3.1 保真度声明（不能省）

设备上今天**没有**真正的"自身语音"检测器：`voiceprint_gate` 只有接口、主工程没接模型，
IMU 也没进主工程。因此 `main/controller.cpp` 的 `own_voice_proxy()` 用
"近场电平优势 × 语音判据"做**占位**证据。

> **已知缺陷：附近有人大声说话会被误判成佩戴者开口。**
> 接入真正的检测器（骨传导 IMU 或声纹门控）时，只替换这一个函数，
> 状态机与全部时序参数都不动。

判定逻辑有 `--replay` 离线验证入口，三种情形——有下压/无下压/无说话——都已用合成数据测过）

| 轮次 | 条件 | 结果 |
|---|---|---|

3. 耳机麦克风被宿主占用时该功能被抑制；
4. 与聆听模式/自适应音频相关。

在测到之前，`Params` 里的数字是**待标定值，不是 Apple 的实测值**。

## 7. 已知偏差（迁移带来的行为变化）

- **下压与调音模式解耦**：安静环境下自己说话也会下压；旧实现把下压挂在
  `external_voice_intent` 分支里，所以"环境判据 = quiet → FLAT"时不会下压。
  这是刻意的：Apple 这条功能不挑模式。
- **`conversation` 字段语义变化**：`LIKELY` 从"轮次成形的对话"变成"佩戴者正在说话（正在下压）"。
  协议字段与上位机未改，面板文字不变。

## 9. 回放验证（2026-10-16，无人在场也能跑）

### 9.1 状态机本身是对的

- `speech-01`：第 62 拍下压、第 87 拍开始恢复 —— 触发、保持、恢复三个相位都跑到了；
- `selfvoice`：187 秒里 131 拍处于下压，恢复相位正常结束；
- 全部 8 个素材都没有出现"压下去起不来"。

### 9.2 暴露的两个问题（都不是状态机的问题）

1. **近场代理不是可用的自身语音判据。** `throat_clear-01` 拿到 own_voice = 1.00 并压到 25% ——
   清嗓子被判成"我自己开口"。这与 Apple 自己的用户抱怨方向一致（清嗓/咳嗽/独白都会触发），
   但**在我们这里它是靠电平而不是靠骨传导判出来的**，所以没有可调的选择性。
2. **素材口径的坑又出现了（与状态总表 38h 同源）。** 这批素材是 Mac 麦克风录的，而判据阈值是在
   设备 ES7210 上标定的：`silence` 素材竟有 37/75 拍被判成语音，而真正的 `speech` 素材只有 5/93 拍。
   **这组数字不能用来改设备判据**，只能说明"用 Mac 麦克风素材验证触发选择性"这条路走不通。

### 9.3 所以下一步是换证据，不是调参数

`Params` 里的数字解决不了 9.2：问题在**证据本身**。两条已确认的路线：

- **IMU 骨传导**（Apple 的思路）：自身语音在六轴上有稳定的低频振动特征，与"旁边有人说话"可分离；
- **声纹门控**：`main/voiceprint_gate.hpp` 的接口已经在了，缺的是模型与素材。

两条都需要先在**设备**上录素材（不是在 Mac 上录），否则会重复 9.2 的口径错误。

## 10. 设备端标定素材采集（第一次真机跑通）

### 10.1 为什么要设备口径

第 9 节已经把"用 Mac 麦克风素材验证触发选择性"判了死刑（与状态总表 38h 同源）。
触发标定必须用**设备自己听到的音频**。

### 10.2 16 kHz 是设备端录音的物理上限

README「端侧录音」一节已经算过：48 kHz 单声道 base64 约 **128 kB/s**，串口可用吞吐
约 **92 kB/s**（139%，不可用）。所以设备端素材是 16 kHz，**24 段里 8 kHz 以上的频段
不能用这批素材判定**。判据真正用到的 300–4000 Hz 语音带在 16 kHz 下是完整的。

### 10.3 采集脚本

```bash
# 先让出串口（上位机面板会占着它）
CORES3_PORT=/dev/cu.usbmodem101 sh tools/free_port.sh --kill
./.venv/bin/python tools/collect_conversation_evidence.py \
    --port /dev/cu.usbmodem101 --speaker 甲 --verify
# 采完原样拉回面板
cd tools && nohup ../.venv/bin/python -u -m host --port /dev/cu.usbmodem101 \
    --web-port 8787 --no-browser &
```

类别按**谁在说**分家，这是对话感知与"24 段判据"最本质的区别：

| 类别 | 期望 |
|---|---|
| `self_speech_near`（设备在嘴边 10–20 cm，自己说） | **应该**触发 |
| `self_speech_far`（设备在桌上，自己 1 m 外说） | 触发与否取决于证据质量 |
| `other_speech_near` / `other_speech_1m`（别人说） | **不应该**触发 |
| `podcast`（手机放播客/视频） | 不应该触发 —— 旧轮次启发式会在这里误触发 |
| `throat_clear` / `hum_long` / `breath` / `silence` | 不应该触发 |

每条落盘 WAV + sidecar JSON（时长、块数、丢块、电平、相对本底、可用性）。
**有丢块的录音直接标 `usable=false`**，脚本返回非零，不静默补零。

### 10.4 第一次真机结果：基线就是坏的

2026-10-16 18:40，设备在线、上位机让出串口，采了一条 `silence`（4.01 s、201 块、丢块 0、
电平 −36.7 dBFS），立刻回放：

```
类别          拍数   语音拍   下压拍   最低%   own峰值   判定
silence        75      35      35      25     0.60   DUCKED
```

**设备自己录的"安静"，被判成语音 35/75 拍，并一路压到 25%。**

⚠️ **口径更正（同日晚些时候）**：这条数字是拿 **16 kHz** 设备素材重采样到 48 kHz 之后跑出来的，
而 8 kHz 以上按定义是空的 —— 按第 10.2 节**自己的口径**，涉及高频段的判据（频谱平坦度、峰度）
在这种素材上是失真的。所以 "35/75" 只说明"**用 16 kHz 素材 + 回放工具判不出设备行为**"，
**不能**当成"近场代理在真机上会把静音判成语音"。

真机上代理到底怎么样，由第 12 节的 **C5（证据是否成立）** 与 **C9（旁人说话不得下压）**
用设备自己 48 kHz 的分析链路回答。这条更正留在文档里，是因为犯错的正是"拿失真素材下强结论"
这件事本身——与状态总表 38h 是同一类错误。

另外两条限制不变：这只有**一条**素材；而且它证明的是"当前证据不可用"，不足以给出任何阈值。
**要改的是证据，不是门限** —— 与第 9.3 节同一个结论。

## 11. 骨传导自身语音证据（IMU 进主工程）

### 11.1 为什么必须换证据

Mac 素材不能判定设备（38h），而设备侧那条记录本身也被 16 kHz 素材的口径问题削弱了
（见 10.4 的更正）。近场代理的判据是"语音判据 × 电平"，它没有"这是不是我"的信息。Apple 用的是**内耳麦克风 + 加速度计**的骨传导证据，这一节就是补上它。

### 11.2 搬了什么

| 来源（experiments/ear-context） | 落到主工程 |
|---|---|
| `components/bmi270`（Bosch 官方驱动） | `components/bmi270/` |
| `main/imu.cpp/.hpp`（100 Hz、±4g、±500°/s，先探测 0x68/0x69，映射 DRDY 中断） | `main/imu.cpp/.hpp`（原样，含"没有 DRDY 映射就会静默失败"那条注释） |

新增 `main/bone_voice.hpp/.cpp`：**判据本体**，纯逻辑、无 I2C、无任务调度，因此能在主机上
用合成信号完整测试（18 条断言）。

### 11.3 判据：包络同步，不是振动频谱

100 Hz ODR 的 Nyquist 只有 50 Hz，看不到骨传导语音振动的频带（100–1000 Hz）。但**看得见包络**：
自己说话时，加速度计的振动幅度与音频的语音带电平会**同步起伏**（音节率 2–8 Hz）。
别人说话、外放、走动都不会产生这种同步。所以判据是相关性：

```text
加速度模长 → 去重力（~0.08 Hz 高通）→ 每 100 ms 桶内 RMS（振动包络）
音频 → 第 8–16 段（300–4000 Hz）平均电平
两者在 800 ms 窗内做 Pearson 相关 → 相关性 × 振动幅度 ×（运动否决）
```

想直接看振动频带需要把 ODR 提到 400 Hz 以上，那是下一步。

### 11.4 接线（固件）

```text
app_main：imu_init()  ← **同步、先于音频任务**（见下面的总线理由）
   └─ 队列（深 64）→ 控制任务每拍全部取出 → bone_voice.push_imu(模长, t)
imu_task（5 ms 轮询，100 Hz 采样，优先级 4，低于音频控制任务的 6）
控制任务（100 ms 一拍）→ bone_voice.push_audio(语音带电平, t) → 置信度
   └─ controller.set_own_voice_evidence(evidence)
```

**为什么 IMU 初始化放在 app_main 而不是采样任务里**：BMI270 与音频编解码器**共用 BSP 的
I2C 总线**（`bsp_i2c_init()` 是幂等的，有 `i2c_initialized` 守卫，共享本身没问题）。但音频控制
任务的优先级是 6、IMU 任务是 4，若由 IMU 任务去初始化，音频任务会在初始化中途抢占它，
两次 I2C 驱动安装/设备注册就可能交错。**ear-context 那个实验里两个任务是同级（5），不会互相抢占，
所以照搬它的写法在优先级不同的主工程里并不等价。** 同步初始化同时拿到了"IMU 先于音频"这个
已验证的顺序。IMU 任务栈取 6144（与 ear-context 相同尺寸），不用未验证过的 4 KB。

配对是 1:1 的：控制拍 100 ms、IMU 100 Hz，一拍正好 10 个采样。

### 11.5.1 缺证据时 fail-closed（2026-10-16 决定）

证据来源只有三种状态，遥测里必须分开报：

| `own_voice_source` | 含义 | 会不会下压 |
|---|---|---|
| `bone` | 骨传导 IMU 证据 | 会 |
| `near_field` | 近场代理兜底（调用方**显式**打开开关） | 会 |
| `none` | 没有证据，fail-closed | **不会** |

**为什么默认不拿代理兜底**：代理的判据是"语音判据 × 电平"，它在设备自己录的静音素材上把
**35/75 拍**判成语音并压到 25%（第 10.4 节），而且分不出"自己说"和"旁边人说"。让它在 IMU
挂掉时兜底，等于把"特征暂时不工作"变成"音乐时不时无故被压"——后者难查得多。
代理本身保留：回放工具（`tools/conversation_replay.cpp`）显式打开开关继续用它检验判据形状，
产品路径默认不经过它。

回归断言：`test/controller_test.cpp` 的 "clear speech with no own-voice evidence does not duck
(fail-closed)" 与 "the proxy fallback still exists when a caller opts in"。

### 11.5 测试抓到的两个真 bug（都不是调参）

1. **重力基线时间常数不能靠近相关窗**：第一版取 2 s、窗 0.8 s，基线把"说 3 拍停 1 拍"的起伏
   当成重力吸掉，振动 RMS 变成近似常数、相关系数归零。结论写进了 `Params::gravity_tau_s` 的注释。
2. **RMS 丢符号**：第一版测试用"整拍直流偏置"当振动，于是高通的输出被基线漂移主导、
   相关系数变成 **−1**。真实加速度计读到的是"重力直流 + 振动交流"，所以测试信号改成 20 Hz 正弦；
   这条物理假设也写进了注释——否则下一个人会再踩一次。

另外运动判据的 2 s 时间常数在 2.4 s 内只走到 70%，摸不到 0.35 的门限；改成 500 ms
（走动要在半秒内被认出来，那半秒宁可不触发）。

## 12. 真机验证脚本

`tools/verify_conversation_awareness.py`。它把第 11.6 节那四项做成可重复的检查，并且**按说话人分相**，

### 12.1 相位与检查

```text
baseline      静置 10 s      → IMU 就绪、重力基线、静止证据应接近 0
self_speech   自己说话 12 s  → 骨传导证据成立、来源必须是 bone、下压时序
quiet_after   安静 10 s      → 媒体恢复
motion        拿起走动 10 s  → 运动否决生效、不得下压
other_speech  旁人说话 12 s  → 不得下压（可用 --skip-other-speech 跳过）
```

| 检查 | 断言 |
|---|---|
| C1 | 固件是 v3（带自身语音遥测）。**这是闸门**：旧固件直接拒绝跑，避免得出假结论 |
| C2 | 静止相 ≥90% 帧 `imu_ok=true` |
| C3 | 静止相 `imu_gravity` p50 ∈ [9.0, 10.5] m/s²（±4g、单位是 m/s²） |
| C4 / C4b | 每相帧率 ≥80%；整个验证过程 `imu_drops` 增量为 0 |
| C4c | 每相 IMU 采样率 ∈ [90, 110] Hz —— "跑在 100 Hz"必须是量出来的 |
| C5 / C5b | 说话相 own_voice 峰值 ≥0.30 且比静止相高 ≥0.15；来源是 `bone` |
| C6 | 证据（≥0.5）到下压（<60%）≤ **650 ms**（确认 200 ms + 3τ） |

## 13. 真机数据标定：骨传导证据在本设备上**不成立**（2026-10-16）

### 13.1 为什么要做这一步

`bone_voice` 的阈值（`vibration_full`、`corr_min`、`motion_veto`、重力时间常数）全部是在**合成正弦**
上定的。上机前先用**真机数据**验一遍，比在设备旁发现判据不动要便宜得多——而且这个仓库里
**已经有真机数据**。

数据：`experiments/listening-model/data/real/20261015T102045Z-selfvoice/`（ear-context 采的）
——100.1 Hz 六轴、186 秒、8 段人工标签（`silent` / `self_speech` / `fidget` / `chew_nod` /
`speech_music`），另有宿主麦克风录音。会话用途写着 "self-voice separability probe from IMU only"。

⚠️ **这批会话数据是本地数据**：`experiments/.gitignore` 忽略 `**/data/`，所以它不在仓库里。
两个工具（导出脚本与回放工具）在仓库里，结论数字也抄进了本节；换机器重跑需要先有数据。

### 13.2 方法（可复现）

```bash
./.venv/bin/python tools/export_bone_real.py \
    experiments/listening-model/data/real/20261015T102045Z-selfvoice \
    记录/对话感知标定/bone-real-selfvoice.csv
g++ -std=c++17 -O2 -I main -o /tmp/bone_real tools/bone_real_replay.cpp main/bone_voice.cpp
/tmp/bone_real 记录/对话感知标定/bone-real-selfvoice.csv
```

- 导出脚本把音频的语音带（300–4000 Hz）包络与 IMU 时间轴对齐：用"说话段 vs 非说话段"的
  包络对比度搜索偏移（δ=+7.5 s，8.71 dB；δ=0 时 7.45 dB——**曲线在 δ=0 附近几乎持平**，
  所以这条对齐只能当趋势看，脚本会自己说明）。
- 回放工具用的是 `main/bone_voice.hpp` 的**同一份代码**，不是 Python 重写。

### 13.3 结果

| 段（真机标签） | 振动 RMS 中位 | 相关中位 | 置信度中位 | 置信度峰值 |
|---|---|---|---|---|
| silent | 0.0144 | +0.02 | **0.000** | 0.69 |
| **self_speech** | **0.3846** | −0.05 | **0.000** | 0.64 |
| silent | 0.1007 | −0.08 | 0.000 | 0.74 |
| fidget（抖腿） | 0.0102 | −0.05 | 0.000 | 0.34 |
| silent | 0.0115 | +0.07 | 0.000 | 0.53 |
| chew_nod | 0.0099 | +0.08 | 0.000 | 0.82 |
| silent | 0.0097 | +0.13 | 0.000 | 0.10 |
| speech_music（外放+说话） | 0.0136 | +0.10 | 0.000 | 0.80 |

另测（同一份数据，10 Hz 振动包络的调制谱）：

| 段 | 振动 RMS 中位 | 2–8 Hz 调制能量占比 |
|---|---|---|
| silent | 0.0124 | 10.9% |
| self_speech | 0.3627 | 25.7% |
| fidget | 0.0098 | **46.7%** |
| speech_music | 0.0132 | 24.8% |

三条读数：

1. **置信度中位在每一段都是 0.000**，包括 `self_speech` —— 判据按其设计不会触发。
2. **振动包络与音频包络的相关在所有段都接近 0**（中位 −0.08…+0.13），也就是**没有测到与语音同步的振动**。
3. 唯一高振动的是 `self_speech` 段（0.38 m/s²，是其他段的 30 倍），而**同样有说话的 `speech_music` 段只有 0.013**
   —— 如果那是骨传导，两段都该高。加上 2–8 Hz 调制能量最高的是 `fidget`（抖腿，46.7%），
   这份高振动更合理的解释是**那一段的身体运动**，不是语音。

### 13.4 与既有结论一致

这个仓库 10 月已经用**另一套特征**（`acc_rms`/`jerk`/`acc_band_speech`/`gyro_*` 等 11 个，
LOSO 分类）测过同一件事：

```json
{"loso_auc": 0.0508, "accuracy_at_0.5": 0.582, "verdict": "基本不可分，建议停"}
```

两套互不相同的判据，同一份数据，同一个答案。**所以骨传导自身语音证据在本设备上不成立。**

### 13.5 必须写清的边界

- 这次会话的 `position` 是 `right-ear`，而 **CoreS3 不是入耳耳机**——它是被贴在耳侧/头侧的开发板。
  骨传导耦合高度依赖"加速度计在耳道里"这件事，所以结论是**"在本设备与本次佩戴方式下不成立"**，
  不是"骨传导不可能"。
- 因此 `bone_voice` 模块**保留**（fail-closed，不触发就不下压），但不宣称它能用；
  真机验证里 **C5 预期会失败**，那是已知结论，不是新问题。
- 想让这条功能真正work，只剩两条路：① 耳戴形态本身（真正入耳的硬件）；
  ② 换证据——声纹门控（需要先录素材，见状态总表第 12 项）。

### 14.2 空跑发现了什么（**不是测量**）

```text
类内相似度  中位 0.3670（范围 0.2479–0.8690）
类间相似度  中位 0.1572（范围 0.0345–0.6176）
间距 / 抖动 = 0.33        EER = 33.33%        → 不通过
```

**这是同一个人**，所以这份数字不能当门控结论。但它显示一件值得警惕的事：
**同一个人的不同条件之间，相似度可以低到像两个人**（0.157 落在类内范围下面）。
这正是姊妹项目栽过的坑 —— 类内抖动（0.15）大于类间间距（0.05）。
所以第 12 项那个止损门**很可能不通过**；不通过也是有用的结论（按判据就该停止声纹路线）。

## 15. 演示模式的证据策略（2026-10-16 决定）

### 15.1 决定

第 13、14 节的结论是：**"佩戴者自己开口"在本原型上没有已验证可用的证据源**。
但演示需要行为可见，所以用户决定：**演示用近场代理**，并且**口径必须如实**。

证据来源因此成为一个显式策略，而不是"有就用"：

| 策略 | 用什么 | 遥测里的 `own_voice_source` | 会不会下压 |
|---|---|---|---|
| `bone_only`（**产品默认**） | 只认骨传导证据；没有就不动作 | `bone` / `none` | 有骨传导证据才会 |
| `near_field_demo`（**当前固件配置**） | 近场代理：语音判据 × 电平 | `near_field` | 会 |
| `disabled` | 什么都不用 | `none` | 不会 |

切换点是 `main/app_main.cpp` 的一行：

```cpp
constexpr EvidencePolicy kEvidencePolicy = EvidencePolicy::near_field_demo;  // 演示
// 产品默认：EvidencePolicy::bone_only
```

### 15.2 为什么策略必须进遥测

`own_voice_source=near_field` 有两种可能：**演示模式的刻意选择**，或者**骨传导挂了在兜底**。
这两种情况的处置完全不同，所以帧里同时带 `own_voice_policy`（`bone_only` / `near_field_demo` /
`disabled`）。面板与串口都能看到它。

### 15.3 演示模式的已知代价（写进检查器）

| 检查 | 在演示模式下 |
|---|---|
| C5 自身语音证据成立 | 含义变成"**有人**在说话"，不是"佩戴者自己" |
| **C9 旁人说话不触发** | **预期失败**：代理分不出自己与旁人。这是已知代价，不是新故障 |
| C5b 证据来源与策略一致 | 必须显示 `near_field`——把它说成骨传导才是错误 |

检查器的 `--selftest` 里有两个对应场景：`demo_policy`（预期 C9 挂）与
`source_mismatch`（把代理报成骨传导时预期 C5b 挂）。

### 15.4 这不是"判据成立"

演示模式解决的是"演示时看不看得见行为"，**不是**"这条功能在真机上成立"。
它成立与否仍然取决于：真入耳的形态（第 13.5 节），或声纹门控通过止损门（第 14 节）。
文档不把这两件事混在一起写，是因为下一轮真机验证时会照着这里读结论。

3. **16 kHz 素材判不了高频段**（第 10.2/10.4 节）：设备端录音的上限是 16 kHz，
   任何涉及 8 kHz 以上频段的结论都不能从这类素材得出——第 10.4 节那条更正就是为此写的。

### 16.5 真机被动检查（2026-10-19，第一次跑）

设备已经在跑本分支固件（`/api/snapshot` 显示 `schema=3`、`evidence_policy=near_field_demo`）。
用新增的 `tools/check_device_passive.py` 从面板接口轮询 90 秒（**不独占串口、不需要人配合**）：

| 检查 | 结果 |
|---|---|
| C1 固件是 v3 | ✅ `schema=[3]` |
| C2 IMU 就绪 | ✅ 801/802 帧 `imu_ok=true` |
| C3 重力基线（±4g） | ✅ p50 = **9.88 m/s²** |
| C4b 丢采样 | ✅ 增量 0 |
| **C4c IMU 采样率** | ❌ **30.1 Hz**（设计 100 Hz；ear-context 当年实测 100.1 Hz） |
| C5b 来源/策略一致 | ⚠️ 同一次轮询里出现过 `bone_only` 与 `near_field_demo` 两种策略（待查） |
| 遥测解析 | ✅ 0 条 anomalies |

**C4c 是这条检查抓到的真问题**：`imu_drops` 增量为 0 说明队列没堵，是**读得慢**。
也就是说"IMU 跑在 100 Hz"这句话在本分支的固件上**不成立**（30 Hz 约为设计值的三成）。
可能原因（未定论）：IMU 任务优先级 4 被音频任务（6）长期抢占、I2C 单次事务耗时、
或控制任务每拍集中排空队列时的总线争用。**根因需要独占串口看日志**，不属于被动检查范围。

对判据的影响：10 Hz 控制拍下一个桶只有约 3 个采样，800 ms 相关窗约 24 点——还能算，
但比设计预期弱。鉴于骨传导判据本身已被第 13 节否定，这不是关键路径；但
**不能继续在文档里写"100 Hz"**，所以在这里更正。

`C5b` 的两种策略并存同样待查（可能是同一次轮询跨越了设备重启/重烧的时刻）。

**同日复测（20 秒窗口）**：7/8 通过——`C5b` 恢复一致（`policy=['near_field_demo']`、
`source=['near_field']`），C2 809/809 帧就绪、C3 重力 p50 9.87、C4b 丢采样 0；
`C4c` 稳定在 **29.2 Hz**，即 30 Hz 附近不是偶发，是稳定值。另观察到演示模式确实在动作：
809 帧里 324 帧下压、最低 `media=60%`——**行为链路在真机上是通的**，问题只在证据与采样率。

## 17. 目标改版（2026-10-19）：从"我开口后下压"改为"预判对话开始"

⚠️ **本节覆盖第 1–16 节的目标设定，但那些章节的实测数字与否定结论仍然有效**（骨传导不可用、
近场代理分不出人、IMU 30 Hz 等）。读旧章节时请记住：它们的"正确答案"是 Apple 的"我开始说才
触发"，而本项目现在的总目标不同。

### 17.1 用户口径（原话）

> 不是碰到我说话的时候压低，是预判我要跟别人讲话了，才压低，这是总目标。一开始是因为
> 反应太慢我才说调整，又调整错了。

### 17.2 为什么旧实现到不了这个目标

旧状态机的**唯一触发输入**是 `Evidence::own_voice`。它只能在"我已经开口"之后成立；首拍预下压
只是把事后反应提前了 100–200 ms。调 `duck_ms`、`preview_floor`、近场代理都改变不了"先检测到
我说话、再下压"这个因果顺序。要预判，必须在**我开口之前**就有证据。

### 17.3 新实现（与 D16 对应）

| 触发 | 动作 |
|---|---|
| `conversation_cue`（附近有人开口；近场电平门 -58…-42 dBFS）第一拍 | `anticipating`：媒体预下压到 70%，**环境声不开** |
| 证据持续 200 ms | `engaged`：媒体压到 60%，`ambient_open=true`（意图） |
| 最后一个人声后 2.5 s 内无声 | `releasing`：恢复媒体、关闭环境声 |
| 短促声（咳嗽/桌椅） | 退回 `idle`，环境声从未动过 |

`own_voice` 保留为可选确认（将来接声纹/骨传导），但**不再是唯一触发**。

环境声的执行：设备只发 `ambient_open` 意图；Mac 用 `tools/host/ambient.py` 调兄弟工程
`airpods-control` 切 AirPods 通透模式，关闭时切回切换前模式。没有 AirPods / 没有 AX 权限 /
CLI 不存在时如实报"执行端不可用"，面板上"意图"与"执行结果"分两行显示。

### 17.4 已知代价与待办

- **会误判"对话冲我来"**：播客、电视、旁边桌说话都能产生 `conversation_cue`。当前没有方向与
  身份信息；止损要靠第 36 项轮次归属（对方说完 → 我是否接话）或声纹/双麦方向。
- **环境声执行是 AX 自动化**，不是公开 API；权限/面板渲染失败都可能发生，必须保留错误显示。
- **旧验证脚本 C9 与新目标冲突**：C9 要求"旁人说话不触发"，但预判式设计的预期行为就是旁人
  开口先压、没人接话再恢复。`tools/verify_conversation_awareness.py` 与 C1–C9 需要按新目标
  重写（把"触发源"换成 cue、把 C9 改成"无接话时 2.5 s 恢复"）。
- 参数（cue 门限、200 ms 确认、2.5 s 保持、60%/70%）全部是**待真机标定值**。
