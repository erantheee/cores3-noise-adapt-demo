# 对话预判：要不要 LLM、训什么、怎么收数

状态：**设计与计划（2026-10-19；2026-10-21 收尾更新）**。当前固件先跑规则版
（`conversation_cue` + 状态机），训练版模型是下一步；v4 遥测已上机（见 §3/§5）。
本文回答两个问题：**要不要用 LLM**、**预判这件事到底怎么训**。

---

## 1. 结论：端侧不用 LLM

| 维度 | LLM 判断 | 小模型 / 规则 |
|---|---|---|
| 延迟 | 首 token 几百 ms 起，端侧更大 | 10 Hz 节拍下 < 1 ms |
| 算力 | CoreS3 上不可行（模型 + 内存） | 线性/树模型，KB 级 |
| 数据 | 没有"对话开始"的标注语料，也没有可用的语义标签 | 10 Hz 遥测即可，人能标 |
| 失效方式 | 语义上说得通但时间上没用：**"这是不是完整对话"不是触发时刻要回答的问题** | 可直接优化"提前多少 ms 触发" |
| 误触发代价 | 不可控 | 可用阈值/迟滞/轮次止损 |

**"是否构成一个完整对话"不需要语义理解。** 触发要做的事是：在**我开口之前**判断"接下来
1–2 秒内会不会进入一来一回的对话"。这是时间结构问题（谁在说、说了多久、停了多久、我是否
接上），不是语言理解问题。LLM 只适合两个离线用途：

1. 离线辅助标注（把录音转成"轮次时间线"给人工核对）；
2. 复盘日志、总结误触发场景。**不进入实时判据。**

> 判据纪律（沿用 D7）：**判据先定后跑**。先写清楚标签定义与止损门，再收数、再训。

> **2026-10-21 补充（D32）**：本节结论不变——端侧实时判据不用 LLM。当日新增的
> ASR/LLM 是对**已经由设备判定为候选**的 6 s 片段做语义确认，用于环境声执行授权
> （`dialogue=yes` 才开放），不是预判触发，也不进 S3。其代价是首开环境声增加约 6–12 s，
> 只用于 demo 的"是否真的在对话"确认；预判与提前量仍由端侧状态机负责。

## 2. 任务定义

在 10 Hz 控制拍上，对每个时刻预测：

```text
y_t = 在 [t, t + horizon] 内，佩戴者是否进入一次"对话轮次"
      （定义了三个子标签，见下）
```

三个可操作子标签（按优先级）：

| 标签 | 定义 | 用途 |
|---|---|---|
| `own_speech_onset` | 佩戴者自己开口的起点 | 最终要"抢在它之前"下压 |
| `reply_after_other` | 对方一段话结束后 0.3–2.0 s 内佩戴者开口 | 轮次预判（真正能提前的那一段） |
| `conversation_active` | 一来一回 ≥2 轮 | 保持/恢复时序 |

**主指标不是准确率，是提前量**：

- `lead_ms = 下压时刻 − 佩戴者首个音节时刻`（目标 > 0，理想 ≥ 300 ms）
- `false_duck_s/h`：播客/电视/独处时被误压的总时长（按小时归一）
- 召回：`P(下压前已触发 | 进入对话)` ≥ 95%

止损门（先写死，达不到就不上线）：`false_duck_s/h ≤ 60`（演示口径）且 `lead_ms p50 ≥ 250 ms`。

## 3. 用什么特征（今天设备上已经有的）

| 特征 | 来源 | 备注 |
|---|---|---|
| 24 段环境谱 `band_dbfs` | 固件 `ambient_band_dbfs` | 10 Hz，已验证可下发 |
| 宽带电平 | 固件 v4 已下发（`broadband_dbfs`） | 判"近场/远场" |
| `voice_likelihood` + 4 个描述量 | 固件 v4 已下发 | 可直接用于训练 |
| 对话状态机状态/时长 | 固件本地 | 作为特征会引入反馈，训练时必须用离线重算 |
| 情境模型 9 类概率 | `listening_model` | 2 s 窗、延迟大；只适合做门控/先验，不做 onset |
| 语音段起止时间 | 由 `voice_likelihood` 序列离线求 | **轮次特征的核心** |
| IMU 运动 | 固件 | 只能做否决，不能做方向（已证） |

**关键特征族是"轮次统计"**，不是单帧频谱：当前语音段已持续多久、上一段语音结束多久、
最近 3 段各自的时长与间隔、是否出现"短句 + 停顿"的对话节奏。

## 4. 模型与集成

1. 先训**逻辑回归 / 小型 GBDT**（10–30 维，10 Hz）。能解释、能限流、导出 C 头文件容易。
2. 不够再上 1 层 GRU（<10k 参数，帧率 10 Hz，端侧可跑）；CoreS3 有足够余量，但优先简单模型。
3. 集成方式：模型输出 `p_conversation` 只替换 `conversation_cue` 的**打分**，状态机
   （anticipating → engaged → releasing）不动。规则版始终保留作为回退与对照。
4. 迟滞与恢复：模型概率 + 状态机 hold/restore 共同决定，禁止单帧翻转。

## 5. 收数与标注（下一步要做的事）

**遥测（2026-10-21 已上机）**：v4 JSON 已带 `broadband_dbfs`、`voice_likelihood` 与 4 个
描述量，另追加了声纹回显 `voiceprint_valid` / `voiceprint_self` / `voiceprint_age_ms`
（只增键，schema 仍 4）。它们也是排查误触发的直接证据。

**采集方案**（复用已经跑通的中继与录音）：

1. 逐帧 JSONL 已可用：上位机 `--frames-jsonl <路径>` 每帧写一行（10 Hz，带时间戳）；
   `tools/collect_teacher_data.py` 会同时落 `audio.wav`、`frames.jsonl` 与 `meta.json`。
2. 同时用 S3 中继录一份 16 kHz 音频（已有通路），用于离线切分语音段与人工复核。
3. 人只标两类时刻：**"我开始跟人说话"**、**"对话结束"**（快捷键/手机计时器均可），
   其余标签由离线 VAD + 规则从音频与遥测推导。
4. 场景至少覆盖：独处（音乐/播客/电视）、两人对话（我/对方先开口）、多人背景聊天、
   走动/拿设备。每条 5–10 分钟，先收 20–30 条再谈训练。

**离线流水线**：`tools/` 下新增（待写）
`log_conversation_dataset.py`（采数）→ `label_conversation.py`（切段/校对）→
`train_conversation_predictor.py`（训练 + 止损门）→ `export_c.py`（导出头文件）。
沿用 `experiments/listening-model/` 的分工：训练侧 Python 是权威实现，固件只做推理，
并用**逐维金标准**钉住移植（同 `context_window_test.cpp` 的做法）。
