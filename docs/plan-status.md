## 目标

把 CoreS3 做成**耳机盒形态的端侧可行性验证机**：在真实约束下量出「AI 处理的延迟」与
「近场拾音的信噪比」两笔硬账，并验证「声纹选人 → 门控 → 目标人提取」这条链路。

给决策者的表述：**同一套补偿逻辑，两个执行者。** 音频链路由播放端负责（这是真实产品的
分工），端侧负责常开感知、判断与决策。唯一变量是"谁在做决策"。

完整论证见 [`edge-feasibility.md`](edge-feasibility.md)，决策理由见 [`decisions.md`](decisions.md)。

`tools/record_from_device.py` 负责**（因为它报告丢块）。

**口径（2026-10-14 用户明确）**：本机只做**增益与调音**，没有降噪。上位机的降噪格子与
趋势图上的降噪曲线都已删除，快照里也不再下发 `noise_reduction_db`；解析层仍校验该字段，
因为"设备报了一个越界的值"依然要能被发现。固件仍在算它、设备屏幕仍写着「降噪」，
那是固件侧待清理的残留（第 19 项）。

**录音回控（第 18 项）已通**：真机验证 `rec start 8` 得到
`{"type":"capture","state":"started","seconds":8,"rate":16000}`，上位机按钮返回
`{"ok":true,"acknowledged":true}`。根因是固件主控制台是 UART0，而 `poll_console_command()`
用 `std::getchar()`——stdout 被路由到 USB 了，**stdin 没有**。修法：
`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` + `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y`。

**但录音的数据速率还没达标（第 18b 项）**：12 秒的录音只产出 2.5 秒音频（约 3.3 k 样本/秒，
目标 16 k）。修好的部分有三处，都有真机实测支撑：

| 缺陷 | 症状 | 现状 |
|---|---|---|
| `Decimator::process` 容量算少 1 个样本 | 第二块起永久返回 0，录音**完全空** | ✅ 已修，单测覆盖 |
| 每个循环把整块喂给抽取器 | 录音里混入上一轮的陈旧样本 | ✅ 已修 |
| 读取与块大小绑定 | 空读 27 万次/10 秒 | ✅ 已修，降到 758 次 |

剩下的是产出速率。设备内诊断（`state:"progress"`）现在会走串口并在面板「设备录音」区显示，
所以下一次不用再猜。

### 已修：串口 DTR（第 16 项）

`tools/monitor.sh`、`tools/record_from_device.py` 与 `tools/drift_capture.py` 原本在打开
串口后设 `dtr = False`，注释说是"别打扰设备"。在本机这块板子上这是反的：

```
dtr=False  10 秒 0 字节        ← 端口能开、能写，永远读不到数据
dtr=True   10 秒 17115 字节    ← 同一台设备、同一份固件
```

**现象是可复现的观察；机制这里要说清楚边界**：能确定的是"本机 macOS + 这块 CoreS3 +
内置 USB-Serial/JTAG"下必须置位才能收到数据（esptool 的 USB-JTAG 复位序列也把
`(DTR=0, RTS=0)` 当作空闲态，所以"芯片物理上不发送"这个因果说法证据不足）。
三个工具现在都改成**只对内置 JTAG 端口**（`/dev/cu.usbmodem*`）置位——因为经典 USB-UART 桥
（CP2102/CH340/FTDI，DTR→IO0、RTS→EN）上置位 RTS 等于把芯片按住复位，症状一模一样。

现场症状和"节点在≠设备在"长得一样（读不到字节），但原因完全不同。三条判据要分开查：
**节点陈旧**看 USB 设备树里有没有 Espressif；**DTR 没置位**看工具里的 modem 线设置；
**端口被占用**看 `lsof`。

## 固件构建（本机没有 ESP-IDF）

本机**没有 ESP-IDF**（`idf.py` 不在 PATH，`~/esp` 是空的），且 GitHub/espressif 直连只有
约 11 kB/s（清华、南大、SJTU、gitee 镜像均不可用），在本机装 IDF 不现实。因此固件改动走
**CI 构建**，用 `gh` 取产物后本地刷写：

```bash
git push origin main                                  # 触发 CI（host-tests → firmware，约 7-8 分钟）
gh run watch                                           # 或 gh run list
gh run download <run-id> -n cores3-noise-adapt-firmware -D /tmp/ci
python3 -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 --baud 460800 \
    write-flash --flash-mode dio --flash-freq 80m --flash-size 16MB \
    0x0 /tmp/ci/bootloader/bootloader.bin \
    0x8000 /tmp/ci/partition_table/partition-table.bin \
    0x10000 /tmp/ci/cores3_noise_adapt_demo.bin
```

回滚靠 `outputs/cores3-pre-demo-backup-20261013.bin`（16 MB 原厂整片备份，
SHA256 前缀 `cfe4efba216fbe59`）。

## 已知的维护风险

- **文档里的数字是手工同步的**：断言总数（178）、真机延迟（150.032 / 7.032 / 0.051 / 1.41 µs）
  都写在 README 与两份 docs 里。改代码不会自动改它们。目前没有 CI 检查，所以**改完代码要
  同时搜一遍这几个数字**。
- 真机数字与固件版本绑定（当前 `be4cba7`）。换版本后必须重新标注出处，否则无法判断某个数字
  是哪个构建测出来的。
- **上位机显示的"帧间隔"是主机侧的到达间隔，不是设备节拍。** 它曾经报 202 ms 而设备自报
  150.04 ms —— 真因是上位机自己：pyserial 的 `read(4096)` 会在一次性的 0.2 s 超时预算里
  等攒满 4096 字节，而设备每次只产出约 180 字节，于是每次读取都必然等满 200 ms。
  改成 `read(in_waiting or 1)` 后实测 p50 = 150.0 ms、min 149.71、max 150.4，与设备一致。
  **报节拍用设备自报的 `capture` 阶段；主机侧那一行只用来判断"上位机有没有跟上"。**
- **`/dev/cu.usbmodem*` 节点在设备拔掉后仍然存在。** 端口能打开、`ls` 能看到，但读不到任何
  字节。不要用"节点在不在"判断设备在不在，要用"能不能读到数据"判断——这一点在采集脚本里
  已加 10 秒快速失败。
