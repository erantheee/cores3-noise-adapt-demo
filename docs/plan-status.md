## 目标

把 CoreS3 做成 **AI OWS 耳机仓原型**：S3 感知和决策，Mac 播放并处理三首固定本地歌曲，
AirPods Pro 播放最终输出；分别验证歌曲 EQ、现实人声增益意图、安全不动作与端到端延迟。

给决策者的表述：**同一套补偿逻辑，两个执行者。** 音频链路由播放端负责（这是真实产品的
分工），端侧负责常开感知、判断与决策。唯一变量是"谁在做决策"。

完整论证见 [`edge-feasibility.md`](edge-feasibility.md)，决策理由见 [`decisions.md`](decisions.md)。

## 真机已测得的数字（第 3、4 项）

固件以 `26789ad` 为基线，加上其后两笔改动——`4308366`（控制节拍此前为 150 ms，该笔改为
**100 ms**，`main/app_main.cpp` 的 `kControlPeriodMs = 100.0f`）与 `3b744cc`（demo 放大到
8.0 dB / 25%）。设备空载、面板 `source=serial`，2026-10-14 实测：

| 阶段 | p50 | 说明 |
|---|---|---|
| 采集间隔 | **100.03 ms** | 设备自报 `capture`，就是控制节拍，目标 100 ms |
| 24 频段分析 | **7.02 ms** | 占节拍约 7% |
| 声纹推理 | 0.0 ms | **未实现**，如实报 0 |
| 决策 | **0.06 ms** | 与打点开销同量级 |
| 打点自身开销 | 1.52 µs | 两次读时钟 |

主机侧到达间隔 p50 = 100.00 ms（这是"上位机有没有跟上"的自检，不是设备节拍）。

**结论**：端侧本机不是瓶颈：分析与决策合计约 7.1 ms，100 ms 节拍下余量约 93%。
**"端侧 AI 很快"这句话仍然不能说**——声纹推理报 0 是因为没有实现，不是因为免费；
见 [`decisions.md` D10](decisions.md)。

## 真机已测得的数字（第 26 项：S3 麦克风 → Mac → 蓝牙耳机）

2026-10-15 实测。固件为当前 HEAD（20 ms 分包；设备自报 `decimated / chunks = 320.1`，
旧固件是 1024 = 64 ms），播放端 `tools/relay/relaysink`，输出设备 AirPods Pro，
连续中继 50 秒：

| 项 | 值 | 出处 |
|---|---|---|
| 播放端排队深度 | **40–60 ms**（上限 60） | 面板「中继延迟」卡，`queued_ms` |
| 驱动侧输出延迟（蓝牙） | **170.7 ms** | `driver_ms`：回调缓冲 512 帧 10.7 + 设备延迟 7680 帧 160.0 |
| **进播放端 → 耳机出声** | **约 211–231 ms** | `est_out_ms` |
| 设备侧打包 + USB | 约 20 ms（打包） | 固件 320 点一块；USB 那一段未单独测 |
| 丢弃 / 启动排空 | **0 ms / 0 ms（50 秒）** | `dropped_ms` / `drained_ms` |
| 送达与播完 | 交付 50.02 s、播完 49.98 s | `delivered_ms` / `played_ms` |

**为什么换掉 ffplay**：它不给反压也不暴露播放位置。实测（`tools/probe_player_buffer.py`）
按实时速率喂 5 秒音频，**0.94 秒就被吞完（吸收比 5.3×）**——它内部囤了多少从外面看不出来，
上位机只能拿"写进去多少字节"当播放进度。实时流的生产速率与播放速率相同，于是任何一次卡顿
造成的积压都**永久保留**，这就是"改了参数延迟只动一点点"的机制。现在排队深度是
"已交付 − 播放器回报已播完"，是回执，不是假设。

**另外两笔与延迟无关但同样致命的账（2026-10-15 现场日志）**：

- 系统默认输出在「AirPods Pro」与「MacBook Air扬声器」之间**来回跳**（158 秒内至少 4 次）。
  每跳一次蓝牙流被拆掉重建，冷启动约 1 秒；而旧播放端照旧往扬声器放，面板只记了一行路由
  变更。用户戴着耳机听不到声音时会去查延迟与缓冲——真正的原因是"声音压根没进耳机"。
  现在中继用 AUHAL 钉住目标设备（不改系统默认输出），目标不在时明确报警。
- 设备上当时跑的是**旧固件**（64 ms 分包）。同一份代码只差这一项就是 44 ms。

**口径（2026-10-14 用户明确）**：本机只做**增益与调音**，没有降噪。上位机的降噪格子与

那是固件侧待清理的残留（第 19 项）。

**录音回控（第 18 项）已通**：真机验证 `rec start 8` 得到
`{"type":"capture","state":"started","seconds":8,"rate":16000}`，上位机按钮返回
`{"ok":true,"acknowledged":true}`。根因是固件主控制台是 UART0，而 `poll_console_command()`
用 `std::getchar()`——stdout 被路由到 USB 了，**stdin 没有**。修法：
`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` + `CONFIG_ESP_CONSOLE_SECONDARY_NONE=y`。

**录音通路（第 18b 项）已达标**：10 秒录音产出 **10.03 秒**音频（157 块、丢块 0）。

这条路上共修了 **6 个缺陷**，全部靠设备内计数器定位（`state:"progress"` 每 5 秒报一次，
面板「设备录音」区直接显示）。没有一个是从读代码猜出来的——这也说明现场必须留着这些计数：

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | 控制台输入没接 USB（stdin 在 UART0） | 录音命令进不去设备 | `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y` |
| 2 | 把 `esp_codec_dev_read` 的**状态码**当字节数（我引入） | 设备完全静默 | 用 `ESP_OK` 判成败，整块推进 |
| 3 | **`Decimator::process` 容量差 1 个样本** | 第二块起永久返回 0，录音**全空** | 容量 `count/k + 2` + `static_assert` |
| 4 | 录音数据耦合进"分析窗口"，窗口满就丢 | 4/5 音频无声丢弃 | 录音直接消费暂存 |
| 5 | 录音期间分析仍抢同一缓冲 | 471 块读取只到 379 块 | 录音时不给分析窗口供料 |
| 6 | 暂存放宽后读取循环因缓冲满空转（我引入） | **设备冻死**，0 字节输出 | 读取每轮最多一次，绝不等待消费者 |

**读法上的两个坑也记下来**：`Decimator::process` 对"输入非法"和"缓冲太小"都返回 0，
调用方分不出来（已写进接口注释）；而控制循环的 `now_us` 看起来是局部的，其实是整个循环的
时基——把读时钟放进任何会被跳过的分支里，设备就会沉默。

### 已修：串口 DTR（第 16 项）

`tools/monitor.sh`、`tools/record_from_device.py` 与 `tools/drift_capture.py` 原本在打开
串口后设 `dtr = False`，注释说是"别打扰设备"。在本机这块板子上这是反的：

```
dtr=False  10 秒 0 字节        ← 端口能开、能写，永远读不到数据
dtr=True   10 秒 17115 字节    ← 同一台设备、同一份固件
```

**现象是可复现的观察；机制这里要说清楚边界**：能确定的是"本机 macOS + 这块 CoreS3 +
内置 USB-Serial/JTAG"下必须置位才能收到数据（esptool 的 USB-JTAG 复位序列也把
`(DTR=0, RTS=0)` 当作空闲态，所以"芯片物理上不发送"这个因果说法证据不足）。
三个工具现在都改成**只对内置 JTAG 端口**（`/dev/cu.usbmodem*`）置位——因为经典 USB-UART 桥
（CP2102/CH340/FTDI，DTR→IO0、RTS→EN）上置位 RTS 等于把芯片按住复位，症状一模一样。

现场症状和"节点在≠设备在"长得一样（读不到字节），但原因完全不同。三条判据要分开查：
**节点陈旧**看 USB 设备树里有没有 Espressif；**DTR 没置位**看工具里的 modem 线设置；
**端口被占用**看 `lsof`。

## 固件构建（本机没有 ESP-IDF）

本机**没有 ESP-IDF**（`idf.py` 不在 PATH，`~/esp` 是空的），且 GitHub/espressif 直连只有
约 11 kB/s（清华、南大、SJTU、gitee 镜像均不可用），在本机装 IDF 不现实。因此固件改动走
**CI 构建**，用 `gh` 取产物后本地刷写：

```bash
git push origin main                                  # 触发 CI（host-tests → firmware，约 7-8 分钟）
gh run watch                                           # 或 gh run list
gh run download <run-id> -n cores3-noise-adapt-firmware -D /tmp/ci
python3 -m esptool --chip esp32s3 --port /dev/cu.usbmodem1101 --baud 460800 \
    write-flash --flash-mode dio --flash-freq 80m --flash-size 16MB \
    0x0 /tmp/ci/bootloader/bootloader.bin \
    0x8000 /tmp/ci/partition_table/partition-table.bin \
    0x10000 /tmp/ci/cores3_noise_adapt_demo.bin
```

## 已知的维护风险

- **文档里的数字是手工同步的**：断言总数（主机 221、上位机 2735、渲染校验 60）、真机延迟
  （节拍 100.03、分析 7.02、决策 0.06）都写在 README 与两份 docs 里。改代码不会自动改它们。
  目前没有 CI 检查，所以**改完代码要同时搜一遍这几个数字**。
- 真机数字与固件版本绑定：当前实测值对应 **100 ms 节拍**（`4308366` 引入）。换版本后必须重新
  测量并标注出处，否则无法判断某个数字是哪个构建测出来的。
- **上位机显示的"帧间隔"是主机侧的到达间隔，不是设备节拍。** 这一项曾经明显大于设备自报的
  节拍——真因是上位机自己：pyserial 的 `read(size)` 会在一次性的超时预算里等攒满 size 才返回，
  而设备每帧只产出几百字节，于是每次读取都必然等满超时才返回，把攒下的几行一次性交给状态归约。
  改成 `read(in_waiting or 1)` 之后，主机侧到达间隔才与设备自报节拍一致。当前 100 ms 节拍下
  实测设备 100.03 ms、主机侧 100.00 ms。
  **报节拍用设备自报的 `capture` 阶段；主机侧那一行只用来判断"上位机有没有跟上"。**
- **`/dev/cu.usbmodem*` 节点在设备拔掉后仍然存在。** 端口能打开、`ls` 能看到，但读不到任何
  字节。不要用"节点在不在"判断设备在不在，要用"能不能读到数据"判断——这一点在采集脚本里
  已加 10 秒快速失败。

## 里程碑口径

对外报数时，每条结论都要带上它的适用边界：

- 分段延迟：端侧本机已实测；音频通路的 311 ms 来自 OWS 的驱动自报值
- 判据：合成信号上已验证假阳性归零，**真实录音上的准确率尚未验证**
- 声纹：策略已实现并单测，**可分性尚未验证**，判据先定后跑
- 双麦、近场 SNR：**尚无结论**，不要提前引用
