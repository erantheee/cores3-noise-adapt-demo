改计划时同步改这里，不要只留在对话里。

## 目标

把 CoreS3 做成**耳机盒形态的端侧可行性验证机**：在真实约束下量出「AI 处理的延迟」与
「近场拾音的信噪比」两笔硬账，并验证「声纹选人 → 门控 → 目标人提取」这条链路。

给决策者的表述：**同一套补偿逻辑，两个执行者。** 音频链路由播放端负责（这是真实产品的
分工），端侧负责常开感知、判断与决策。唯一变量是"谁在做决策"。

完整论证见 [`edge-feasibility.md`](edge-feasibility.md)，决策理由见 [`decisions.md`](decisions.md)。

## 下一步（按优先级，且都需要人在设备旁）

### 立刻可做（不需要设备）

- 上位机 `ows-earbud-demo` 的 `blelink` 对接（第 13 项）——**待确认是否要动已排练的工程**
- 把「录音 → 可分性 → 标定」写成可照做的检查清单

### 需要设备与人的

按顺序，每一步都产出下一轮的依据：

```bash
# 1) 烧录当前固件
sh tools/flash.sh                      # 会打印 SHA256 供核对

# 2) 一小时漂移（让它自己跑）
python3 tools/drift_capture.py --port /dev/cu.usbmodem1101 --seconds 3600 \
    --out 记录/drift.jsonl

# 3) 录判据标定素材：安静本底 / 白噪声 / 1 kHz 纯音 / 正常人声，各 10 秒
#    另开终端往串口发：rec start 10
python3 tools/record_from_device.py --port /dev/cu.usbmodem1101 --baud 921600 \
    --seconds 12 --out 记录/标定-安静本底.wav

# 4) 录近场素材：设备拿在手里 10–20 cm 说话 / 1 m 外 / 嘈杂本底，各 30 秒

# 5) 录声纹素材：同一人**分次、换距离换音量**至少 3 条；另一人 3 条
#    然后跑止损门
python3 tools/voice_separability.py --enroll 甲A.wav 甲B.wav 甲C.wav \
                                   --impostor 乙A.wav 乙B.wav 乙C.wav
```

**声纹那组必须刻意改变条件。** 只在一个条件下录出的"稳定"声纹，在真实使用中不成立——
姊妹项目用 24 频段包络吃过这个亏：类内抖动 0.15 大于类间间距 0.05，不存在可用阈值。

## 已知的维护风险

- **文档里的数字是手工同步的**：断言总数（178）、真机延迟（150.032 / 7.032 / 0.051 / 1.41 µs）
  都写在 README 与两份 docs 里。改代码不会自动改它们。目前没有 CI 检查，所以**改完代码要
  同时搜一遍这几个数字**。
- 真机数字与固件版本绑定（当前 `be4cba7`）。换版本后必须重新标注出处，否则无法判断某个数字
  是哪个构建测出来的。
- **`/dev/cu.usbmodem*` 节点在设备拔掉后仍然存在。** 端口能打开、`ls` 能看到，但读不到任何
  字节。不要用"节点在不在"判断设备在不在，要用"能不能读到数据"判断——这一点在采集脚本里
  已加 10 秒快速失败。

## 里程碑口径

对外报数时，每条结论都要带上它的适用边界：

- 分段延迟：端侧本机已实测；音频通路的 311 ms 来自 OWS 的驱动自报值
- 判据：合成信号上已验证假阳性归零，**真实录音上的准确率尚未验证**
- 声纹：策略已实现并单测，**可分性尚未验证**，判据先定后跑
- 双麦、近场 SNR：**尚无结论**，不要提前引用
